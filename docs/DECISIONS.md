# 설계 결정 기록

시간순이 아니라 주제별로 정리한다. 각 항목은 "무엇을 정했는가"와 "왜"를 함께 남긴다. 세부 근거는 `docs/IMPLEMENTATION_PLAN.md`, 화면 대응은 `docs/PROTOTYPE_MAPPING.md` 참조.

## 화면/UX

**D-1. 학생 홈은 지도형 UI를 유지한다. 프로토타입 HTML을 폐기하지 않는다.**
이전 세션(`docs/IMPLEMENTATION_PLAN.md` 최초 작성 시점)은 프로토타입을 "운영 구조 확정 전에 중단된 화면 실험, 배포 대상 아님"으로 분류했다. 그러나 이는 정정한다 — 이번 지침은 해당 프로토타입이 "정식 웹앱의 화면 경험과 역할 기반 구조를 보여주는 핵심 프로토타입"이며 이를 유지·발전시키는 것이 목표임을 명시한다. 따라서 지도/건물/역할별 분기 UX는 버리지 않고 컴포넌트로 재구성한다(`docs/PROTOTYPE_MAPPING.md`, `docs/ARCHITECTURE.md` §3).

**D-2. 현재 구현된 App.tsx/theme.css의 관리자 패널 톤은 학생 화면의 최종 형태가 아니다.**
1~2단계 코드는 기능(로그인/학교선택/명단가져오기/직업신청)이 정확히 동작하는 것을 우선했고, 실제로 규칙 테스트까지 통과하는 견고한 로직을 갖췄다. 다만 시각적으로는 지도형 프로토타입과 무관한 일반 대시보드 스타일이다. 로직(도메인/데이터 레이어)은 그대로 재사용하고, 학생 대면 화면만 지도/건물 레이아웃으로 다시 감싼다. 교사 화면은 지금의 패널형 톤을 유지해도 된다(원문 §40, §79).

**D-3. 시안 테스트용 역할 선택 드롭다운(`roleSelect`)은 정식 앱에서 제거한다.**
실제 역할은 로그인 계정의 `JobAssignment` 조회 결과로 결정되어야 하며, 학생이 임의로 바꿀 수 없다(원문 §11). 교사용 "역할 미리보기" 기능으로는 축소 유지 가능.

## 계정/데이터 분리

**D-4. Firebase Auth UID와 학생 학적(`studentId`)을 분리된 식별자로 둔다.**
전학, 계정 재발급, 개명이 있어도 직업 이력과 금융 원장을 동일 `studentId`로 유지하기 위함. 학생 명단에 로그인 계정이나 개인 이메일을 요구하지 않는다.

**D-5. 첫 학교/owner 등록은 앱 자체 가입 폼으로 하지 않는다.**
일반 앱 경로로 멤버십을 쓸 수 있게 하면 역할 승격(학생→교사) 위조 경로가 열린다. 최초 등록은 Firebase 콘솔 또는 별도 신뢰된 관리 도구로 한정하고, `firebase/firestore.rules`는 `members` 하위 쓰기를 전부 거부한다.

## 금융

**D-6. 학생 클라이언트가 잔액/원장을 직접 쓰는 경로는 만들지 않는다.**
버튼을 숨기는 것만으로는 `개발자 도구로 balance+10000` 같은 조작을 막을 수 없다(원문 §50). 모든 금융 실행은 서버(교사 세션의 트랜잭션)에서 재계산·검증한 뒤 확정한다. 학생은 요청자, 은행원 학생은 검토자, 교사가 승인 실행자다.

**D-7. 완료된 거래는 수정·삭제하지 않고 반대 방향 정정 거래를 추가한다.**
원장의 불변성을 지키기 위함. 관리자(Admin SDK/콘솔)가 규칙을 우회할 수 있다는 한계는 별도로 명시하며 "어떤 관리자도 절대 바꿀 수 없다"는 과장된 보장은 하지 않는다.

**D-8. 이자는 단리, 월 단위(달력 월 기준), basis points 정수로 계산한다.**
학교 운영이 1년 단위이므로 연이율보다 월이율이 교육적으로 이해하기 쉽다. `30일×개월수` 방식 대신 달력 월과 월말 보정을 사용해 실제 학사 일정과 어긋나지 않게 한다. `src/domain/money.ts`의 `simpleInterest`/`addCalendarMonths`가 이미 이 결정을 구현하고 있다(half-up 반올림, BigInt 연산).

**D-9. 금융 자동화는 초기에는 "계산은 자동, 실행은 교사 세션 의존"으로 제한한다.**
Firebase Spark(무료) 플랜은 유료 Cloud Functions/스케줄러를 지원하지 않는다. 정시 무접속 자동 정산은 처음부터 약속하지 않고, 교사가 접속해 "이번 달 정산" 버튼을 누르는 흐름으로 시작한다. 안전성이 검증된 개별 연산(예: 단순 구매)부터 단계적으로 즉시 처리로 승격할 수 있다.

## 사진/증빙

**D-10. Cloud Storage(Blaze 필요) 대신 압축된 임시 사진을 Firestore 문서에 Base64로 저장한다.**
카드 등록 없는 Spark 운영 목표와 충돌하기 때문. 대신 크기 제한(긴 변 640px, 약 60KB), 짧은 만료(24시간), 승인 시 삭제를 강제한다. "즉시 자동 삭제"는 접속 기반 정리이므로 보장하지 않음을 UI에 명시한다.

## 직업/조직

**D-11. 직업 수를 학교 규모에 고정하지 않는다. 핵심국 4개 + 유연한 세부 직업.**
학생 수가 줄거나 늘어도 같은 코드베이스로 운영 가능해야 한다(원문 §2). 핵심 직업은 hard delete 대신 상태 전이(preparing→recruiting→active→paused→closed)로 관리해 과거 배정/업무 기록을 보존한다.

**D-12. 신청(Application)과 배정(Assignment)을 분리된 컬렉션으로 둔다.**
직업당 여러 신청자가 있을 수 있고, 배정은 승인 결과로만 생성되어야 하므로 이력 추적과 권한 검증이 쉬워진다. 문서 ID를 `jobId~studentId`로 결정적으로 만들어 중복 신청/중복 배정을 규칙 레벨에서 방지한다(현재 `firestore.rules`에 구현됨).

## 업무(Task) 1차 구현

**D-14. 업무 제출 이력을 별도 컬렉션으로 분리하지 않고 Task 문서 1건에 접는다(v1 한정).**
원문·`IMPLEMENTATION_PLAN.md` §5의 정식 설계는 `tasks`/`submissions`/`evidence`를 분리해 제출 시도마다 별도 문서를 남긴다. 1차 구현에서는 학생이 재제출할 때마다 원자적 상태 전이(getAfter 교차검증)를 위해 두 컬렉션을 함께 트랜잭션으로 검증해야 하는데, 이는 Firestore Rules에서 상당한 복잡도(문서 간 존재·정합성 교차 검증)를 요구한다. 대신 Task 문서 자체에 `attempt`(제출 횟수, 감사용 카운터)와 `submissionText`(최신 제출 내용만)를 두어, 학생 제출/교사 검토/재시작을 모두 **하나의 문서에 대한 단일 업데이트**로 표현했다. 결과: 이전 제출 시도의 텍스트는 재제출 시 사라진다(과거 값 보존 안 됨). §52(배열/거대 필드로 계속 늘어나는 기록을 저장하지 말 것)는 위반하지 않는다 — 애초에 이력을 누적하지 않기 때문이다. 실제 운영에서 제출 이력 감사가 필요해지면 `submissions` 서브컬렉션을 추가하고 Task는 "현재 상태 투영"으로 남기는 방향으로 분리한다.

**D-15. 업무 인증 방식은 1차로 `artifact`(결과물 제출)만 UI로 노출한다.**
`photo`/`system` 인증은 원문 §14-15가 요구하는 사진 압축·임시 저장·만료 처리, 또는 실제 이벤트(도서 대여, 판매 등) 연동이 필요해 각각 별도 구현 단계다. 타입과 Firestore Rules의 enum(`artifact|photo|system`)은 세 값을 모두 허용해 스키마 마이그레이션 없이 확장 가능하게 해 두었지만, 교사가 업무를 만드는 화면에서는 `artifact`만 선택 가능하다. 이유: 절반만 동작하는 기능(예: 사진 인증을 선택했는데 실제로 사진을 찍을 수 없는 화면)을 노출하지 않기 위함.

**D-16. 업무 배정은 "해당 직업의 활성 배정을 가진 학생"만 대상으로 서버에서 강제한다.**
`tasks` 컬렉션의 `create`/`restart` 규칙은 `jobAssignments/{jobId~studentId}`가 `status=='active'`인지 `get()`으로 교차 확인한다. 학생이 이미 그만둔 직업으로 새 업무를 배정받거나, 애초에 맡은 적 없는 직업의 업무를 받는 경로를 rules 단계에서 차단한다.

## 금융(계좌·월급) 1차 구현

**D-17. 첫 금융 거래 종류로 SALARY만 구현하고, journal을 SALARY 전용 형태로 좁힌다.**
원문·`IMPLEMENTATION_PLAN.md` §5의 정식 `journals` 설계는 `sourceType`/`sourceId`/`policyVersionId`를 갖는 다형적(polymorphic) 구조로 모든 거래 종류(SALARY/DEPOSIT/PURCHASE/INTEREST 등)를 하나의 문서 모양으로 표현한다. 1차 구현에서는 아직 그 다형적 구조를 검증할 다른 거래(구매, 저축, 대출 등)가 하나도 없는 상태에서 일반화된 규칙을 먼저 짜는 것은 추측성 설계다("don't design for hypothetical future requirements"). 대신 `journals` 문서에 `jobId`/`studentId`/`period` 같은 SALARY 고유 필드를 직접 두고 `type=='SALARY'`만 허용했다. 저축/대출/구매 등 다음 거래 종류를 추가할 때 실제 필요에 맞춰 다형적 형태로 넓힌다.

**D-18. `lastJournalId` + `getAfter`로 "원장 없이는 잔액도 없다"를 규칙 레벨에서 강제한다.**
계좌 문서에 `lastJournalId`(직전 반영 journal의 ID)를 두고, 계좌의 모든 생성·수정 규칙은 `getAfter(journals/{lastJournalId})`로 같은 트랜잭션에서 만들어진 journal을 되짚어 그 journal의 차변/대변 계좌·금액이 지금 이 잔액 변화와 정확히 일치하는지 검증한다. 즉 "이 트랜잭션이 유효한 journal을 만들었다"는 사실 없이는 어떤 계좌 update/create도 통과할 수 없다. 이 덕분에 별도의 `operationKeys` 컬렉션 없이도 **journal 문서 ID 자체(`salary~{jobId}~{studentId}~{period}`)가 멱등성 키**가 된다 — 같은 키로 재시도하면 이미 존재하는 journal에 대한 "update"로 취급되고, journal은 `allow update, delete: if false`라 무조건 거부된다. 재시도는 안전하게 아무 효과도 내지 않는다.

**D-19. 시스템 발행 계좌(`system-issuer`)를 두어 복식 원장을 실제로 복식으로 유지한다.**
월급은 "누군가의 계좌에서 빠져나가는" 돈이 아니라 학교가 새로 발행하는 돈이므로, 상대편이 필요하다. 학교마다 정확히 하나 존재하는 `system-issuer` 계좌(음수 허용)가 차변이 되고 학생 계좌가 대변이 된다. 전체 시스템의 계좌 잔액 총합은 항상 0이 되어(발행액의 음수 + 학생들의 양수 합) 원장이 실제로 대사(reconcile)된다.

**D-20. `accounts/{accountId}` 문서의 읽기 권한은 `resource.data`가 아니라 경로 변수로 판정한다.**
처음에는 `resource.data.ownerType=='student' && ownStudent(sid,resource.data.ownerId)`로 짰으나, Firestore 규칙에서 **존재하지 않는 문서**를 `get`할 때 `resource`가 없어 `resource.data` 접근 자체가 평가 오류(=거부)로 이어진다는 사실을 에뮬레이터 테스트로 직접 확인했다. 즉 한 번도 월급을 받은 적 없는 학생은 자기 계좌를 조회하려 할 때마다 권한 오류를 받게 된다. 계좌 ID를 학생 ID와 같게 만들어 두었으므로(`accountId==ownerId`), 대신 `ownStudent(sid,accountId)`처럼 **경로 변수**로 판정하도록 고쳤다 — 문서가 있든 없든 항상 평가 가능하다. 앞으로 계좌 이외의 "본인 소유 문서, ID=studentId" 패턴에도 이 교훈을 적용한다.

**D-21. 학생 대면 은행 화면은 계좌 조회만 제공하고, 저축·대출·구매·이자·세금·과태료는 전부 다음 단계다.**
지도의 "은행" 건물이 처음으로 실제 데이터에 연결됐지만, 지금은 "내 잔액 + 최근 거래" 열람과 (교사 쪽) 월급 정산만 동작한다. `financialRequests`(학생 요청)/`financeReviews`(은행원 학생 검증) 워크플로는 아직 없다 — 지금은 요청·검토 단계 없이 교사가 직접 정산을 실행한다. 학생이 무언가를 "신청"하는 최초의 금융 상호작용(저축 가입, 대출 신청)이 생기는 시점에 그 워크플로를 도입한다.

## 사업·상점 1차 구현

**D-22. 사업은 교사가 직접 만든다. 시민 제안·투표를 거친 승인은 아직 없다.**
`IMPLEMENTATION_PLAN.md` §5는 "승인된 사업만 생성"이라 못박지만, 그 승인 파이프라인(시민 제안 → 투표 → 교사 결정, 6단계)이 아직 없다. 직업도 같은 이유로 교사가 직접 만들며(1~2단계 그대로), 사업도 동일한 선례를 따른다. 6단계가 생기면 "제안 승인 → 사업 생성"을 하나의 트랜잭션으로 묶는 작업이 필요하다.

**D-23. 구매는 교사 정산 없이 학생이 즉시 실행한다 — 월급과는 다른 신뢰 모델이다.**
월급은 "학생 요청 → 은행원 검토 → 교사 정산"을 거치지만(D-9), 구매는 은행원 확인 없이 **결제 버튼을 누르면 즉시 완료**된다. 원문 §19 "즉시 자동 확정이 필요한 저축·구매·송금은 각 연산을 보안 규칙으로 완전히 검증할 수 있을 때 별도 단계로 연다"는 조건을 만족했다고 판단한 이유: 가격·재고·잔액을 모두 서버(Rules)에서 그 자리에서 재확인하고, 학생은 오직 자기 계좌를 빚지는 것과 사업 계좌를 정확히 그 금액만큼 늘리는 것만 할 수 있다(잔액을 더 깎거나 사업 계좌를 더 늘릴 방법이 없음). 40명 학생이 매점을 이용할 때마다 교사가 하나씩 승인해야 한다면 실제로 운영이 불가능하다는 현실적 이유도 있다.

**D-24. 별도 `orders` 컬렉션을 만들지 않는다. journal + entries가 곧 구매 기록이다.**
구매가 즉시 확정이라 "처리 중" 같은 중간 상태가 없으므로, 원문이 상정한 주문 처리 흐름(주문접수→완료)이 필요 없다. 사업이 나중에 실물 수령 확인 같은 절차를 필요로 하면 그때 `orders`를 분리한다. 수량도 1개 고정으로 단순화했다 — 여러 개를 사려면 같은 상품을 여러 번 구매한다.

**D-25. 사업 계좌는 학생 소유자 전용 열람도, 학생 간 비공개도 아니다 — 교사 전용 + 구매 시 상대방 열람만 허용한다.**
사업 운영 학생이 자기 사업의 매출 내역을 보는 기능은 이번 범위에 없다(후속 단계). 다만 라운드트립 중 실제로 필요했던 것은: 구매하는 학생이 트랜잭션 안에서 **상대(사업) 계좌의 현재 잔액을 읽어야** 정확한 증가분을 계산해 쓸 수 있다는 점이었다. 그래서 사업 계좌는 "존재하는 사업의 계좌라면 활성 멤버 누구나 조회 가능"으로 열어 두었다 — 계좌 소유자 필드가 아니라 `businesses/{accountId}` 문서의 존재 여부로 판정한다(학생 개인 계좌 정보를 노출하는 것과는 다른 성격이라고 판단).

**D-26. (재사용 가능한 교훈) `exists()`/`get()`은 트랜잭션 이전 상태, `getAfter()`는 트랜잭션 이후 상태 — 같은 트랜잭션에서 만드는 문서는 반드시 `getAfter()`로 확인한다.**
사업 계좌 생성 규칙에서 `exists(businessPath(accountId))`로 "사업이 존재하는가"를 확인했다가 실패했다 — 사업 문서 자체가 **같은 트랜잭션에서 함께 생성**되고 있었기 때문에, 트랜잭션 커밋 이전 시점 기준인 `exists()`는 항상 거짓이었다. `getAfter()`로 바꾸자 해결됐다(에뮬레이터 테스트로 직접 재현·검증). 저축·대출처럼 "여러 문서를 한 트랜잭션에서 함께 만드는" 다음 기능에서 똑같은 함정을 만날 수 있다 — **한 트랜잭션 안에서 새로 쓰는 문서를 참조할 때는 항상 `getAfter()`, 이미 존재가 보장된(다른 트랜잭션에서 이미 커밋된) 문서를 참조할 때는 `exists()`/`get()`**을 쓴다.

## 시민광장(제안·투표) 1차 구현

**D-27. 제안 종류는 직업·사업 2가지만 구현한다. 규칙·행사·커뮤니티는 다음 단계다.**
원문(§34)은 JOB/BUSINESS/RULE/EVENT/COMMUNITY 5종을 상정하지만, 승인 시 실제로 무언가가 "생성"되는(JobRole, Business) 유형은 이 둘뿐이다. RULE/EVENT/COMMUNITY는 승인해도 만들어질 대상 컬렉션이 아직 없어(§37 "승인된 RULE → Rule 생성"의 Rule 엔티티 자체가 없음) 이번 범위에서 제외했다. 두 유형 모두 원문이 요구한 대로 자유 입력 한 칸이 아니라 구조화된 필드(직업추천서 7항목, 사업제안서 10항목)를 강제한다.

**D-28. 제안 제출은 즉시 반영되고, 투표 시작은 교사가 별도로 결정한다.**
`제안 흐름: draft → submitted → voting → closed → teacher_review → approved/rejected → implemented` 전체를 그대로 옮기지 않고 `submitted → voting → closed → approved/rejected`로 좁혔다. `draft`(임시저장)와 `teacher_review`를 분리된 상태로 두지 않은 이유: 학생이 제출한 시점에 이미 완성된 제안이라고 가정하고(초안 저장은 다음 단계), "검토"는 교사가 `investing 시작` 버튼을 누르기 전까지의 `submitted` 상태 자체가 곧 검토 대기 상태를 겸한다. 마감·최소 참여율·찬성 기준은 투표를 시작하는 이 시점에 교사가 정하며(원문 §38), 제안 제출 시점에는 정해지지 않는다.

**D-29. 투표 집계는 교사 클라이언트가 계산해서 제출한 값을 신뢰한다 — Rules가 subcollection을 세어 재검증하지 않는다.**
Firestore 보안 규칙은 서브컬렉션 문서 개수를 집계하는 연산을 지원하지 않는다(Cloud Functions 없이는 불가능 — Spark 무료 제약과 충돌). 원문도 "소규모 학교는 마감 후 교사가 실제 votes를 읽어 집계하고 스냅샷을 남긴다"고 명시해 이 한계를 인정한다. 대신 개별 투표(`votes/{uid}`) 자체는 규칙으로 완전히 보호한다 — 학생 한 명당 정확히 한 표, 투표 중이고 마감 전일 때만, 자기 계정으로만. 즉 "누가 어떻게 투표했는가"는 위조 불가능하지만 "합계를 정확히 옮겨 적었는가"는 다른 교사 조작들과 같은 수준의 신뢰에 의존한다.

**D-30. 승인은 결정 문서 갱신 + 실제 엔티티 생성을 한 트랜잭션으로 묶고, 제안 상태 자체가 재시도 방지 키 역할을 한다.**
새 직업/사업의 문서 ID를 `proposal-{proposalId}`로 결정적으로 만들어(§37 "생성 ID는 proposalId에 묶어 재시도 중복을 막는다") 재시도 시 같은 ID로 다시 만들려는 시도가 자연히 막힌다. 또한 제안 자체의 `status`가 `closed`에서 한 번만 `approved`/`rejected`로 전이할 수 있으므로, 두 겹의 보호가 있다. 승인 시점에 직업의 소속국·아이콘·권장학년(사업이면 담당 학생)을 교사가 추가로 정하는데, 이는 학생 제안서에는 없던 운영 정보이기 때문이다 — 제안서 내용과 실제 생성되는 문서 사이의 필드 일치는 규칙에서 엄격히 대사하지 않는다(교사가 이미 넓은 권한으로 직업/사업을 직접 만들 수 있는 것과 같은 신뢰 수준).

**D-31. (재사용 가능한 교훈) Rules의 특수 경로 리터럴(`/databases/$(db)/documents/...`)에서는 세그먼트 안에 문자열과 `$(변수)`를 섞어 쓸 수 없다.**
`/accounts/proposal-$(proposalId)`처럼 리터럴 텍스트와 바인딩을 같은 세그먼트에 이어 쓰면 컴파일 자체가 깨진다(다른 여러 줄이 줄줄이 파싱 오류로 번짐). 해결: `accountPath(id)` 같은 헬퍼 함수를 만들어 `accountPath('proposal-'+proposalId)`처럼 문자열 연결은 함수 인자 단계에서 끝내고, 경로 리터럴 안에는 완성된 변수 하나만 `$(id)`로 바인딩한다. 이번에 `accountPath`를 새로 추가했다 — 이제 `businessPath`/`productPath`/`journalPath`/`jobPath`/`assignmentPath`/`taskTemplatePath`/`accountPath`까지 모든 컬렉션에 이 패턴이 일관되게 적용되어 있다.

**D-32. (참고) 서브컬렉션을 모두 읽어야 하는 작업은 일반 목록 상한(100)보다 넉넉한 별도 상한이 필요할 수 있다.**
투표 집계는 "일부만 보고 넘어가면 안 되는" 작업이라 `bounded()`(최대 100)로는 학생 수가 100명을 넘는 큰 학교에서 집계가 깨진다. `boundedVotes()`(최대 500)를 별도로 두었다 — 일반 관리 화면 목록은 여전히 100건으로 제한해 읽기 비용을 아끼고, "전수 확인이 꼭 필요한" 작업만 예외를 둔다.

## 사진 증빙(사진 인증) 1차 구현

**D-33. 사진은 항상 브라우저에서 재인코딩해 JPEG로만 저장한다 — 원본 파일 형식·EXIF를 신뢰하지 않는다.**
`<canvas>`에 그려서 다시 JPEG로 뽑아내는 과정 자체가 EXIF를 제거하고(캔버스는 원본 메타데이터를 들고 있지 않음) SVG 등 실행 가능한 형식을 무력화한다(래스터화되어 항상 픽셀 이미지가 됨). 별도의 "허용 형식 검사"보다 안전하다 — 무엇을 넣든 결과물은 항상 안전한 JPEG다. 목표 크기(긴 변 640px, 약 60KB)를 못 맞추면 품질을 6단계까지 낮추고, 그래도 안 되면 제출을 거부한다(원문 §15의 "압축 후 최대 약 60KB" 기준).

**D-34. 증빙은 업무(Task)당 최신 1장만 존재한다 — 시도별 이력을 남기지 않는다.**
D-14(제출 텍스트를 최신 1건만 보존)와 같은 이유·같은 범위 결정이다. 증빙 문서 ID를 taskId와 같게 만들어 "이 업무의 현재 진행 중인 사진"이 항상 최대 1건임을 구조로 보장한다. 승인·반려 어느 쪽이든 검토가 끝나면 증빙을 즉시 삭제한다 — 원문은 "승인 시 삭제"만 명시하지만, 반려 시에도 학생이 새로 촬영해 재제출해야 하므로 이전 사진을 보관할 이유가 없고, 개인정보(사진)를 최소 기간만 두려는 원칙(§15 "불필요한 원본 사진 삭제")에는 더 부합한다.

**D-35. 만료(24시간) 이후 물리 삭제는 교사 접속 시 소량씩(`purgeExpiredEvidence`, 최대 20건) 처리한다 — 접근 차단은 규칙으로 즉시.**
Spark 무료 플랜에는 예약 Functions나 TTL이 없다(원문 §33, §16의 명시된 제약). `expiresAt`이 지난 문서는 규칙에서 즉시 조회 거부되므로(학생·교사 모두) "보이지 않게 됨"은 실시간이지만, 문서 자체의 삭제는 교사가 다음에 접속했을 때 일어난다. 이 둘을 하나의 "자동 삭제"로 뭉뚱그려 표현하지 않는다(D-5의 §12-5와 동일한 구분).

**D-36. (재사용 가능한 교훈) 압축 ID(`templateId~studentId`처럼 `~`를 포함하는 값)를 규칙의 일반 ID 정규식에 넣지 않는다.**
`evidenceShape()`의 `taskId` 필드에 다른 곳과 같은 `^[A-Za-z0-9_-]{1,100}$` 정규식을 그대로 복사해 썼다가, 실제 taskId(`tpl1~one`)가 물결표를 포함해 전부 거부되는 버그를 에뮬레이터 테스트로 잡았다. 정규식은 그 필드가 실제로 어떤 값인지(단순 ID인지, `~`로 합성된 복합 ID인지)를 보고 정해야 한다 — 다른 곳의 정규식을 습관적으로 복사하면 안 된다.

**D-37. (D-20의 재발) 소유권을 경로만으로 판정할 수 없는 리소스는 "삭제된 뒤 조회"가 조용한 오류로 샌다 — 호출부에서 흡수한다.**
계좌(D-20)는 `accountId==studentId`라 경로만 보고 판정할 수 있었지만, 증빙은 소유자가 태스크의 배정 대상이라 경로(taskId)만으로 판정할 수 없다. `get` 규칙에 `resource!=null &&`를 앞에 두어 "존재하지 않으면 깨끗하게 거부"까지는 만들 수 있었지만, 그래도 결과는 "빈 문서"가 아니라 "권한 거부"다. `getEvidence()`가 이 거부를 `catch`로 흡수해 호출부에는 "사진 없음"(`null`)으로 통일해 보여준다 — 검토 화면이 만료/삭제/미제출을 구분하지 못해도 학생 경험에는 문제가 없기 때문이다.

## 운영(통계·감사·학적) 1차 구현

**D-38. 감사 로그는 "민감한 교사 결정" 3가지에만 우선 붙인다 — 모든 쓰기를 기록하지 않는다.**
원문 §62가 예로 든 항목(금융 정정, 대출 승인, 과태료, 세율 변경, 금융상품 변경, 사업 승인, 직업 승인) 중 지금 실제로 구현된 것은 제안 승인/반려(직업·사업 승인에 해당), 사업 생성, 월급 지급이다. 이 세 곳에만 감사 로그 기록을 추가했다 — 직업 신청 승인이나 업무 검토처럼 이미 그 자체로 이력이 남는(jobApplications, tasks 문서가 상태 전이를 보존) 작업까지 중복으로 기록하지 않는다. 감사 로그는 "이 결정이 왜/누구에 의해 내려졌는가"를 요약해 두는 목적이지, 모든 쓰기의 사본이 아니다.

**D-39. 감사 로그는 `schemaVersion`을 두지 않는다 — append-only 로그는 스키마가 거의 바뀌지 않는다.**
다른 모든 컬렉션은 `schemaVersion`을 갖지만, 감사 로그는 (a) 한 번 쓰이면 절대 수정되지 않고 (b) 구조가 이미 최소한(누가/언제/무엇을/어디에)이라 마이그레이션 필요성이 낮다. 불필요한 필드를 추가하지 않는다는 원칙을 따랐다.

**D-40. 감사 로그의 집계 정확성은 규칙이 아니라 "쓰기를 트랜잭션에 포함시켰는가"에 의존한다.**
각 로그는 실제 상태 변경과 **같은 트랜잭션**에서 기록된다(제안 결정, 사업 생성, 월급 지급 모두). 즉 로그가 있다는 것은 그 결정이 실제로 커밋됐다는 뜻이고, 거꾸로 결정이 커밋됐는데 로그가 빠지는 경우는 없다(트랜잭션이 원자적이므로 성공 시 로그도 함께 성공한다).

**D-41. 학생 학적 상태(졸업/전출) 변경은 기존 `students` 갱신 규칙을 그대로 쓴다 — 새 규칙이 필요 없었다.**
1단계에서 이미 `status` 필드를 교사가 바꿀 수 있게 열어 두었지만(원문 §5 "졸업/전출은 데이터 삭제 대신 멤버십 비활성화 및 학적 상태 변경부터 처리한다") 그동안 이를 실행할 화면이 없었다. 이번에 교사 명단 화면에 수정 폼을 추가했을 뿐, 서버 쪽 권한 모델은 바뀌지 않았다 — 이미 안전하게 설계되어 있었다는 뜻이다. 로그인 계정(membership) 비활성화는 여전히 앱 밖의 관리 도구 영역이다(D-5).

**D-42. 통계 대시보드는 새 집계 쿼리를 만들지 않고, 이미 화면들이 불러오는 목록을 재사용해 개수만 센다.**
전체 학생·직업·업무·사업·제안 수를 보여주는 화면을 별도 카운터 문서나 집계 전용 쿼리 없이, 각 기능이 이미 갖고 있는 `load()`/`loadCatalog()`/`loadProposals()` 호출을 한 번씩 더 실행해서 클라이언트에서 세는 방식으로 만들었다. Firestore 읽기 비용을 새로 추가하지 않으면서(어차피 각 화면을 열면 발생하는 읽기와 동일한 크기), 별도 백엔드 없이 운영 현황을 보여준다.

**D-43. 학교 간 격리·비용·전체 사용자 흐름은 이미 누적된 86개 에뮬레이터 테스트로 검증되어 있다 — 새 테스트를 추가하지 않았다.**
1~7단계에서 만든 모든 규칙 테스트 파일이 예외 없이 "다른 학교 접근 거부" 케이스를 포함한다(학생·교사 양쪽에서, 모든 컬렉션에 대해). Firebase 무료 사용량 절약 원칙(목록 100건 상한, 실시간 리스너 미사용, 사진 압축)도 1~7단계에서 이미 각 기능에 내장되어 있다. 8단계에서 이를 다시 증명하는 새 테스트를 추가하는 대신, 기존 스위트가 이미 이 기준을 충족한다는 사실을 확인하고 문서화하는 쪽을 택했다.

## 학생 로그인 방식(이메일 없이 학교 코드·학년·이름)

**D-44. 학생 로그인은 "학교 코드·학년·이름 + 비밀번호"이고, 내부적으로만 합성 이메일을 만들어 Firebase Auth에 넘긴다.**
Firebase Authentication의 이메일/비밀번호 로그인은 문자열이 이메일 **형식**이기만 하면 되고, 실제로 받는 편지함일 필요는 없다. 원문 §4가 이미 "학생의 개인 이메일이 반드시 필요하다고 가정하지 않는다"고 못박아 뒀지만 구체적인 방식은 정하지 않았었다. `{학교코드}-{학년}-{이름}@students.jobedu.local` 형태로 결정적으로 합성한다(`src/domain/studentAuth.ts`). 처음에는 학년+반+이름(명단 가져오기의 기존 중복 판정 키)으로 설계했지만, 실제 학교(학년당 1개 반)에서는 반 입력이 불필요한 타이핑이라는 피드백을 받아 학년+이름으로 줄였다 — 학년당 반이 여러 개인 학교에서 같은 학년에 동명이인이 있으면 로그인이 겹치므로, `create-student-accounts` 스크립트가 실행 전 이 충돌을 검사해 발견되면 계정 생성을 멈추고 알린다(그런 학교는 반을 다시 식별자에 넣어야 한다). 학교 코드를 더한 이유는 Firebase Auth 계정이 프로젝트 전체에서 유일해야 하는데(스쿨 단위가 아님) 두 학교에 같은 학년·이름 조합이 있을 수 있기 때문이다. 이것은 "이름만 입력하는 로그인"(원문 §4가 명시적으로 금지)이 아니다 — 학생마다 다른 비밀번호가 여전히 필요하다.

**D-45. 로그인 화면은 학생/선생님 탭으로 나뉘고, 학교 코드는 태블릿별 URL(`?school=코드`)로 미리 채울 수 있다.**
공유 태블릿에 학교 코드까지 포함한 북마크(`https://.../?school=jobedu-5c8fb`)를 걸어 두면, 학생은 매번 학년·이름·비밀번호만 입력하면 된다. 선생님 탭은 기존 이메일 로그인을 그대로 유지한다(성인 계정은 실제 이메일을 쓰는 것이 자연스럽고, 첫 교사 계정도 이메일로 부트스트랩하기 때문).

**D-46. 학생 계정(로그인) 발급은 앱이 아니라 오프라인 관리 도구(`scripts/admin-bootstrap.mjs`)가 한다 — Admin SDK가 Rules를 우회하기 때문이다.**
원문 §4 "Firebase Admin은 규칙을 우회하므로 학교 단위 검증·작업 미리보기·감사 로그를 별도로 구현한다"와 D-5(멤버십 쓰기는 앱 안에서 전부 거부)를 그대로 따른다. 이 스크립트는: (1) 학교 생성, (2) 교사/원장 계정 생성(이메일), (3) **이미 가져온 명단을 읽어** 학년+이름 충돌이 없는지 먼저 검사하고, 없으면 학생별로 계정이 없을 때만 만들어 6자리 무작위 비밀번호를 CSV로 출력한다. 같은 명령을 다시 실행해도 이미 있는 계정은 건너뛴다(재실행 안전). 이 CSV는 실명·비밀번호를 담고 있으므로 `.gitignore`의 `*.csv` 규칙에 이미 걸려 커밋되지 않으며, 교사가 출력 후 직접 학생에게 나눠주고 파일은 안전하게 보관·삭제해야 한다.

**D-47. 서비스 계정 키는 앱 코드에 포함하지 않고, 사용자가 로컬에 내려받아 스크립트 실행 시에만 경로로 전달한다.**
`*firebase-adminsdk*.json`, `serviceAccountKey*.json` 패턴을 `.gitignore`에 추가해 실수로 커밋되는 것을 막는다. 이 키는 프로젝트 전체에 대한 관리자 권한을 가지므로 채팅이나 저장소에 절대 붙여넣지 않는다.

## 저축 1차 구현

**D-48. 저축 가입은 구매(D-23)와 같은 신뢰 모델을 쓴다 — 은행원 검토 없이 학생이 즉시 실행한다.**
원문 §20은 대출에 "은행원 검토 → 필요 시 교사 승인"을 명시하지만, 저축에는 그런 사람의 판단 단계를 요구하지 않는다(§13-19). 실제로 저축 가입은 원금·기간이 상품의 min/max 범위 안인지와 잔액이 충분한지만 확인하면 되고, 이는 Rules가 트랜잭션 안에서 그 자리에서 완전히 검증할 수 있다 — PURCHASE가 가격·재고·잔액을 그 자리에서 재검증하는 것과 동일한 성격이다(D-23). `financialRequests`/`financeReviews`(§5 표)는 이번에도 도입하지 않았다: 그 워크플로가 정말로 필요한 것은 사람의 판단이 들어가는 대출이며, 검증된 두 번째 구체 사례 없이 먼저 일반화하지 않는다는 D-17의 원칙을 그대로 따른다. 대출을 구현할 때 저축(첫 번째 구체 사례)과 대출(두 번째 구체 사례) 둘을 놓고 `financialRequests`의 실제 필요한 모양을 일반화한다.

**D-49. 이자는 가입 시점이 아니라 만기 정산(교사 세션) 시점에만 계산·확정한다 — Rules 언어로 `simpleInterest()`를 재구현하지 않는다.**
`simpleInterest()`(`src/domain/money.ts`)는 BigInt 기반 half-up 반올림을 쓰는 이미 테스트된 순수 함수다. 이를 Firestore Rules DSL(정수 연산, 반올림 규칙이 다를 수 있음)로 그대로 재현하려 하면 두 구현이 미묘하게 어긋날 위험이 있다. 대신 가입 시 Rules는 `productSnapshot.rateBpsMonthly`가 상품 문서의 실제 값과 정확히 일치하는지만 검증해 "가짜 이율"로 가입하는 것을 막고, 실제 이자 금액은 만기 정산 화면(기존 `previewSalary`/`settleSalary`와 정확히 같은 미리보기→확정 구조)에서 교사 세션의 앱 코드가 계산해 INTEREST journal에 쓴 뒤, Rules는 그 journal의 금액이 `저축 계약의 principalMinor + interestMinor`와 정확히 일치하는지만 대사(reconcile)한다. 이는 지금 SALARY가 `job.salaryMinor`를 그대로 신뢰하는 것과 동일한 신뢰 수준이며, 새로운 패턴이 아니다. 만기 전 정산 자체를 Rules가 막지는 않는다 — SALARY도 정산 월(period) 선택을 전적으로 교사 클라이언트에 맡기는 것과 같은 신뢰 수준이고, `previewMaturities()`가 만기 도래분만 나열해 정상적인 사용 경로에서는 애초에 문제되지 않는다.

**D-50. 원장 거래 종류 `SAVINGS_DEPOSIT`(가입)·`INTEREST`(만기)를 `JournalType`에 좁게 추가한다 — 다형적 journal로 일반화하지 않는다.**
D-17이 정한 대로, `journal.type`을 여전히 폐쇄 열거형으로 유지하고 허용 값만 늘린다. `SAVINGS_DEPOSIT`은 학생 계좌→`system-issuer`(원금이 학교의 저축 풀로 들어감), `INTEREST`는 `system-issuer`→학생 계좌(만기에 원금+이자 전액 반환)로, 기존 `creditedHere()`/`debitedHere()`의 `journalActorOk()` 기반 범용 로직을 그대로 재사용한다(추가 규칙 변경 없음) — SALARY/PURCHASE가 이미 증명한 debit=지불자/credit=수취자 패턴을 그대로 따르기 때문이다.

**D-51. 만기 정산의 journal id(`interest~{contractId}`)는 D-18과 동일한 멱등키다.**
가입 시 journal id는 `savingsDeposit~{contractId}`(contractId는 클라이언트가 만드는 fresh id — PURCHASE와 같은 신뢰 수준, 재시도 시 서로 다른 계약이 생기는 것을 감수한다). 반면 만기 정산의 journal id는 계약 id에서 결정적으로 파생되므로, 같은 계약을 두 번 정산하려는 시도(예: 오래된 미리보기 캐시로 재시도)는 이미 존재하는 journal을 다시 만들려는 시도가 되어 `allow update, delete: if false`에 걸려 조용히 실패한다 — `settleMaturities`는 이를 트랜잭션이 반환하는 `'skipped'` 결과로 구분해 카운트한다(단순히 `catch`로 흡수해 `paid`를 잘못 증가시키지 않도록, 기존 `settleSalary`의 카운팅 방식보다 한 단계 더 정확하게 만들었다).

## 대출 1차 구현

**D-52. 대출 상환은 저축 가입과 같은 신뢰 모델(학생 즉시 자기실행)을 쓰고, 1차 구현은 전액 일시상환만 지원한다.**
원문 §20이 대출에 요구하는 "은행원 검토 → 필요 시 교사 승인"은 대출 **실행(원금을 내줄지 판단)**에 대한 것이지, **상환(갚을 금액을 갚는 것)**에 대한 것이 아니다 — 상환액은 계약(`totalOwedMinor`)에 이미 고정돼 있고 잔액이 충분한지만 확인하면 되므로 규칙이 그 자리에서 완전히 검증할 수 있다(구매/저축가입과 같은 신뢰 수준, D-23/D-48). 분할·중도상환은 `IMPLEMENTATION_PLAN.md` §6이 저축의 중도해지에 대해 이미 미뤄 둔 것과 같은 이유(별도 상환 정책 설계가 필요)로 다음 단계로 미룬다. `LoanContract`에 `repaidMinor` 필드는 원문이 요구한 "상환 기록"을 위해 남겨 뒀지만, 1차 구현에서는 항상 0 또는 `totalOwedMinor` 둘 중 하나만 갖는다(부분값을 갖지 않음).

**D-53. 대출 검토자 배정은 "은행원 직업을 가진 학생"을 강제하지 않는다.**
원문 §21은 검증이 "실제 직업 업무가 된다"고 하지만, 학교마다 은행원 job의 존재·id가 다를 수 있고(교사가 직업을 삭제·개명 가능) 이를 하드코딩하면 깨지기 쉽다. `assignReviewer`는 jobApplications 승인이 이미 그렇듯 교사가 활동 중인 학생 아무나를 지정할 수 있게 한다 — "이 학생이 실제로 은행원 직업을 맡았는지"는 교사의 판단에 맡긴다(신뢰 수준은 다른 교사 배정 작업과 동일). 은행원 업무와 대출 검토를 실제 Task 시스템으로 엮는 것은 별도 통합 작업이며 이번 범위가 아니다.

**D-54. `financialProducts`를 저축·대출 공용 `FinancialProduct`(`kind:'savings'|'loan'`)로 일반화한다 — 이제 검증된 두 번째 구체 사례가 있기 때문이다.**
저축 1차 구현 때는(D-48) "두 번째 구체 사례 없이 먼저 일반화하지 않는다"(D-17)는 이유로 상품 타입을 `kind:'savings'` 고정 리터럴로 좁게 유지했다. 이제 대출이 정확히 같은 필드(이율·기간·금액 범위·상태)를 필요로 하는 두 번째 사례로 확인됐으므로, `validateFinancialProduct`/`validAmount`/`validMonths`(`src/domain/savings.ts`에 있던 `validateSavingsProduct`/`validSavingsAmount`/`validSavingsMonths`를 일반화해 `src/domain/finance.ts`로 이동)와 `financialProducts` 컬렉션의 `kind` 검증(`=='savings'`→`in ['savings','loan']`)을 공유한다. 같은 이유로 `journals`의 저축 전용 shape 검증기 `savingsDepositJournalShape`/`interestJournalShape`도 `studentToIssuerJournalShape`/`issuerToStudentJournalShape`로 일반화해 `SAVINGS_DEPOSIT`/`LOAN_REPAYMENT`와 `INTEREST`/`LOAN`이 각각 재사용한다 — 네 거래 종류 모두 "학생 하나 ↔ system-issuer, `{studentId,contractId}`로 식별" 형태가 완전히 같기 때문이다. 상품 CRUD(`listProducts`/`createProduct`/`closeProduct`)도 `src/data/financialProductRepository.ts`로 옮겨 저축·대출 스토어가 공유한다.

**D-55. (재발 방지 기록) 저축 가입이 `system-issuer` 계좌를 갱신하지 않던 버그를 대출 구현 중 발견해 고쳤다 — 학생이 상대 계좌를 읽어야 하는 트랜잭션에는 `accounts` get 규칙이 별도로 필요하다.**
대출 상환(`repay`)을 저축 만기 정산(`settleMaturities`)과 대칭으로 구현하려고 보니, 저축 가입(`openSavings`)이 애초에 학생 계좌만 차감하고 `system-issuer` 쪽은 한 번도 갱신하지 않았다는 것이 드러났다 — D-19가 약속한 "전체 계좌 잔액 합은 항상 0" 불변식이 저축 경로에서는 실제로 지켜지지 않은 채 배포까지 됐던 것이다(구매/월급은 원래 양쪽을 다 갱신하고 있어 문제없었다). 저축 가입에 issuer 계좌 갱신을 추가하면서 동시에 새 문제가 드러났다: `accounts/{accountId}` 규칙의 `get`은 `teacher(sid) || ownStudent(sid,accountId) || exists(businessPath(accountId))`였는데, 학생이 자기 트랜잭션 안에서 `system-issuer`(accountId가 자신의 studentId도 아니고 business도 아님) 계좌를 읽으려 하면 거부됐다 — 이는 대출 상환에서도 똑같이 발생할 문제였다. 두 경우 모두 학생이 "상대방"(issuer) 계좌의 현재 잔액을 읽어야 정확한 증가분을 계산해 쓸 수 있다는, 사업 계좌에 이미 적용했던 것과 같은 이유(D-25)다. `accountId=='system-issuer'`를 get 조건에 추가해 해결했다 — 발행 계좌 잔액은 특정 학생의 개인정보가 아니라 학교 전체의 공유 정보이므로(사업 계좌와 같은 성격) 노출에 문제가 없다고 판단했다. **재사용 가능한 교훈**: 학생이 자기 자신 외의 계좌를 트랜잭션에서 다루는 새 기능을 만들 때는, 그 계좌에 대한 `get` 권한이 실제로 있는지 먼저 확인한다 — 트랜잭션 로직만 맞고 read 권한을 빠뜨리면 에뮬레이터에서 "evaluation error"로만 나타나 원인을 즉시 알기 어렵다.

## 학생 비밀번호 재설정 (교사 인앱 셀프서비스)

**D-56. 교사가 앱 안에서 학생 비밀번호를 재설정하는 기능은 Firebase Cloud Functions가 아니라 Cloudflare Workers로 구현했다.**
브라우저는 원칙적으로 남의 Firebase Auth 비밀번호를 절대 바꿀 수 없다(서비스 계정 자격 증명을 브라우저에 넣으면 개발자 도구로 즉시 탈취 가능) — 이런 "교사가 검증된 뒤에만 실행되는 서버 로직"은 어떤 식으로든 브라우저 바깥의 신뢰된 실행 환경이 필요하다. Firebase 자체의 Cloud Functions는 사용량이 0이어도 Blaze(종량제, 카드 등록 필수) 요금제를 요구하는데, 이 프로젝트는 카드 등록 없이 진행하기로 했다(사용자 결정). Cloudflare Workers 무료 티어는 카드 등록 없이 정확히 같은 역할(서비스 계정 자격 증명을 비밀 저장소에 보관하고, 검증된 요청에만 응답)을 할 수 있어 이쪽을 선택했다. 대가로 Firebase 프로젝트 하나로 끝나지 않고 Cloudflare 계정·`cf-worker/` 배포를 별도로 유지해야 한다 — 학교 하나 규모에서는 감수할 만한 트레이드오프로 판단했다.

**D-57. `cf-worker`는 Firebase Admin SDK 대신 Google REST API(OAuth2 JWT-bearer + Identity Toolkit/Firestore REST)를 직접 호출한다.**
`firebase-admin` Node SDK는 Cloudflare Workers 런타임(Node 내장 모듈이 없는 V8 isolate)에서 동작하지 않는다. 대신 서비스 계정의 `client_email`/`private_key`로 직접 RS256 JWT를 서명해(`jose`, WebCrypto 기반이라 Workers에서 동작) `https://oauth2.googleapis.com/token`에서 OAuth2 액세스 토큰을 받고, 그 토큰으로 Firestore REST(`GET .../schools/{id}/members/{uid}`, 교사 권한 확인용)와 Identity Toolkit REST(`accounts:lookup`/`accounts:update`, 학생 계정 조회·비밀번호 변경용)를 직접 호출한다. 요청자 신원은 클라이언트가 보낸 Firebase ID 토큰을 Google의 공개 JWKS로 직접 검증해(`jose`의 `createRemoteJWKSet`) 확인한다 — Firebase Admin SDK가 내부적으로 하는 것과 동일한 신뢰 모델이며, 별도 세션이나 자체 발급 토큰을 두지 않는다.

**D-58. `accounts:lookup`/`accounts:update`는 API 키가 아니라 OAuth 토큰으로 호출하므로 `https://identitytoolkit.googleapis.com/v1/accounts:*` 경로를 그대로 쓴다(`projects/{id}/accounts:*`가 아니어도 동작함을 확인).**
처음엔 "API 키 대신 OAuth를 쓸 때는 `projects/{projectId}/accounts:*` 경로가 필요할 것"이라 추측하고 그렇게 의심했으나, curl로 직접 두 경로를 나란히 비교해보니 둘 다 정상 동작했다 — 실제 원인은 별개로, 테스트에 쓴 curl 명령이 한글이 섞인 JSON을 셸 인자로 바로 넘기면서 인코딩이 깨져 "학생을 찾을 수 없음"으로 잘못 보였던 것이었다(파일로 써서 `--data-binary @file`로 넘기니 정상 동작). **재사용 가능한 교훈**: 한글(또는 비ASCII) 문자열이 포함된 JSON을 curl로 테스트할 때는 `-d '...'` 인라인 인자를 쓰지 말고, 항상 파일에 써서 `--data-binary @file`로 넘긴다 — 그렇지 않으면 애플리케이션 코드가 아니라 셸/터미널의 인코딩 문제를 "버그"로 오인하게 된다. 실제 배포된 Worker 코드 자체는 `fetch(...,{body:JSON.stringify(...)})`를 쓰므로 이 문제와 무관했다(정상 동작을 처음부터 계속 하고 있었음).

## 소득세 1차 구현

**D-59. 소득세는 잔액이 아니라 "그 정산월에 실제로 지급된 SALARY 저널의 합"을 과세 대상으로 삼는다 — 재산세가 아니라 정확히 소득세가 되도록.**
잔액에 과세하는 쪽이 구현은 더 간단했다(계좌의 `balanceMinor`만 읽으면 됨) — 하지만 §23이 명시적으로 "소득세"라고 부르는 것은 그 기간에 번 돈에 매기는 세금이지, 모아둔 재산에 매기는 세금이 아니다. 이미 존재하는 SALARY 저널(정산월별로 결정적 ID를 가짐, D-18)을 학생별로 합산하는 쪽을 택해, 여러 직업을 겸한 학생도 정확히 과세되고 저축·구매로 잔액이 줄어든 것과 세금이 뒤섞이지 않는다. 부작용: 그 정산월에 월급을 아직 지급하지 않은 학생은 미리보기에 나타나지 않는다 — 교사가 월급 정산을 먼저 하고 소득세를 정산해야 하는 순서 의존성이 생기지만, 이는 실제 급여 원천징수의 자연스러운 순서와 같다.

**D-60. `settleSalary`(이미 배포되어 실사용 중인 코드)는 전혀 건드리지 않고, 소득세를 완전히 분리된 후속 교사 세션 정산으로 만들었다.**
월급 지급액에서 세금을 즉시 원천징수하는 설계(한 트랜잭션에서 SALARY+INCOME_TAX 두 저널을 함께 쓰는 것)도 고려했지만, 이미 학생 39명 실계정에 배포되어 쓰이고 있는 `settleSalary`의 계좌 갱신 로직(하나의 트랜잭션 안에서 같은 계좌 문서를 두 번 갱신)을 건드리는 것은 회귀 위험이 컸다. 대신 저축 만기 정산(§21)과 완전히 같은 패턴 — 독립된 미리보기→확정 흐름, 자기 저널 타입(`INCOME_TAX`), 자기 멱등키(`tax~{studentId}~{period}`) — 을 택해 기존 SALARY 경로의 신뢰성에 전혀 의존하지 않는다.

**D-61. `incomeTaxJournalShape()`는 `studentToIssuerJournalShape()`를 재사용하지 않고 새로 만들었다 — 대상 계좌가 다르고(`system-issuer`가 아니라 `community-fund`), 식별 축도 다르다(`contractId`가 아니라 `period`).**
D-54가 저축·대출을 하나의 `FinancialProduct`로 일반화한 것은 "검증된 두 번째 구체 사례가 생겼을 때"였다(D-17). 소득세는 지금 유일한 "학생→system-issuer가 아닌 다른 시스템 계좌" 사례이므로, 같은 원칙에 따라 성급히 일반화하지 않고 `salaryJournalShape()`(정산월 기준)를 본뜬 전용 shape 함수를 만들었다. Rules는 세금액을 SALARY 저널들을 합산해 재검증하지 않는다(여러 문서를 합산하는 집계 쿼리를 보안 규칙이 할 수 없음, D-32와 같은 한계) — INTEREST(D-51)와 같은 신뢰 등급으로, 교사 세션이 계산한 금액을 학생 잔액 하한(음수 방지)만 재확인하고 신뢰한다.

**D-62. `School.incomeTaxRateBp`는 기존 학교 문서에 없는 필드이므로, Rules는 이를 `null`도 허용하고 읽는 쪽은 없으면 0으로 취급한다(D-33의 `lastJournalId==null` 패턴 재사용).**
Firestore의 `updateDoc`은 부분 병합이라, `request.resource.data`는 이번 업데이트가 건드리지 않은 필드까지 포함한 "병합된 전체 문서"를 가리킨다 — 기존 학교 문서엔 `incomeTaxRateBp`가 아예 없으므로, 이 필드를 무조건 `is int`로 요구하면 그 필드를 한 번도 설정한 적 없는 학교는 **다른 어떤 필드(학교 이름 등)도 영원히 수정할 수 없게 막힌다**. `d.incomeTaxRateBp==null || (... is int ...)` 형태로 둘 다 허용해 기존 배포를 깨지 않았다. **재사용 가능한 교훈**: 이미 운영 중인 문서 타입에 새 필드를 추가할 때는 Rules의 유효성 검사를 항상 "없어도 됨"으로 시작하고, 실제로 그 필드가 항상 존재해야 하는 시점(예: 새로 생성되는 문서부터)에만 필수로 강제한다 — 기존 문서를 일괄 backfill하지 않는 한, 무조건 필수로 요구하면 기존 배포가 조용히 전부 잠긴다.

## 사업 운영 학생 자기 관리 1차 구현 (D-25 후속)

**D-63. 사업 소유 학생의 자기 상품 관리·매출 열람은 사업 자체의 생성·종료(생애주기)는 건드리지 않고, "이미 존재하는 사업 안에서의 일상 운영"만 자기 서비스로 열었다.**
D-22가 "사업은 교사가 직접 만든다"고 못박은 이유(원문의 제안·승인 파이프라인이 그때는 없었음)는 시민광장(§17)이 생기면서 이미 해소됐다 — 지금은 학생이 제안 → 투표 → 교사 승인을 거쳐 새 사업을 만들 수 있다. 하지만 이번 범위는 그 이후 단계, 즉 **이미 만들어진 자기 사업**의 상품 추가·가격/재고/판매상태 수정과 매출(계좌 잔액 + 거래 내역) 열람으로 좁혔다. 사업을 닫는 것(`status:'closed'`)은 여전히 교사만 할 수 있다 — 생애주기 결정(사업을 계속할지 말지)까지 학생 재량으로 넘기는 것은 이번 범위가 아니라고 판단했다.

**D-64. `ownBusiness(businessId)`는 새 헬퍼 함수로 추가했다 — `ownStudent`(자기 계좌·명세 판정)와는 판정 대상이 다르다(그 학생 소유의 "사업"인지 vs 그 계좌가 "본인 것"인지).**
`businesses/{businessId}.ownerStudentId`를 신뢰된 소스로 삼아 `get()`으로 직접 조회한다 — 클라이언트가 보낸 어떤 값도 신뢰하지 않는다(§ 권한 판정의 일반 원칙). `products`의 create/update와 `accounts/{accountId}/entries`의 get/list 양쪽에서 재사용했다: 상품은 `resource.data.businessId`(수정 시) 또는 `request.resource.data.businessId`(생성 시)로, 매출 내역은 계좌 문서의 `accountId`가 곧 businessId라는 기존 관례(D-25)를 그대로 따라 조회한다.

**D-65. `saveProduct()`(클라이언트 리포지토리 함수)에서 하드코딩된 `teacher()` 가드를 제거하고, 권한 판단을 전부 Rules에 맡겼다 — `buy()`가 이미 쓰던 신뢰 패턴과 동일.**
`saveProduct`는 상품 생성과 수정을 겸하므로 "지금 호출자가 교사인지 소유 학생인지"를 클라이언트에서 미리 가리려면 추가로 사업 문서를 한 번 더 읽어야 했다 — 그 대신 트랜잭션을 그대로 시도하고, 권한이 없으면 Firestore가 permission-denied로 거부하도록 두었다(`buy()`가 구매 자격을 사전 확인하지 않고 트랜잭션에 맡기는 것과 같은 이유). 부작용 하나를 테스트로 확인했다: 이 변경 전부터 있던 "학생은 상품 재고를 직접 늘리거나 다른 필드를 바꿀 수 없다" 테스트가 실제로 검증하던 것은 소유권이 아니라 "`updatedAt`을 안 넣은 불완전한 write는 `productShape()` 자체에서 거부된다"는 것이었다 — 그래서 그 테스트는 owner 여부와 무관하게 여전히 통과한다(수정하지 않음). 진짜 소유권 판정은 `saveProduct()`(항상 `updatedAt:serverTimestamp()`를 채움)를 거치는 정상 경로로 새 테스트에서 별도 확인했다.

## 사업 세금 1차 구현, 그리고 Rules의 "없는 필드" 함정

**D-66. (긴급 버그 수정, 이미 배포된 코드에 영향) `d.field == null`은 그 필드가 "존재하고 값이 null"일 때만 통하지, 필드가 아예 없는 문서에서는 평가 오류를 던진다 — `d.get('field', null) == null`을 써야 진짜로 안전하다.**
`businessTaxRateBp`를 추가하면서 학교 문서 업데이트 테스트가 `"Property businessTaxRateBp is undefined on object"`로 실패했다 — 재현해보니 D-62에서 "기존 문서에 없는 필드는 nullable하게 허용한다"며 썼던 `request.resource.data.incomeTaxRateBp == null || (...)` 패턴 자체가 처음부터 이 문제를 안고 있었다: 그 필드가 **한 번도 설정된 적 없는** 문서에서는 `d.field`에 접근하는 순간 평가 오류가 나고, Rules 엔진은 그 서브식을 `false`로 취급한다 — 즉 지금까지는 "학교 이름만 바꾸는" 것 같은, `incomeTaxRateBp`를 건드리지 않는 업데이트가 그 필드를 한 번도 설정한 적 없는 학교에서는 **이미 실패하고 있었을 수 있다**(소득세 배포 이후 실제로 그 경로를 아무도 밟지 않아 드러나지 않았을 뿐). 두 필드(`incomeTaxRateBp`, `businessTaxRateBp`) 모두 `request.resource.data.get('필드명', null) == null || (...)` 형태로 고쳤다 — `.get(key, default)`는 키가 없어도 평가 오류 없이 `default`를 돌려준다. **재사용 가능한 교훈**: Rules에서 "이 문서엔 이 필드가 없을 수도 있다"를 표현할 때는 항상 `d.get('field', default)`를 쓴다 — `d.field == null`은 필드가 명시적으로 null로 저장된 경우에만 안전하고, 필드 자체가 없는(never-set) 경우까지 다루지 못한다.

**D-67. 사업 세금도 소득세(D-59)와 같은 원칙 — 사업 계좌 잔액이 아니라 그 정산월의 실제 매출(PURCHASE로 사업 계좌에 들어온 금액)에만 매긴다.**
소득세가 SALARY 저널을 학생별로 합산하듯, 사업 세금은 PURCHASE로 인한 입금만 사업별로 합산한다. 다만 PURCHASE 저널에는 SALARY와 달리 `period` 필드가 없다(이미 배포되어 실사용 중인 `buy()`를 건드리지 않기 위해 그대로 둠, D-60과 같은 이유) — 그래서 정산월 판정은 각 사업 계좌의 `entries` 서브컬렉션에 이미 기록되는 `postedAt`(실제 시각)을 달력월로 변환해 비교하는 방식으로 했다.

**D-68. 전체 학교의 `journals`를 한 번에 쿼리하지 않고, 사업마다 자기 `accounts/{businessId}/entries`를 따로 읽는다 — 복합 색인을 새로 만들지 않기 위해서다.**
`where(type=='PURCHASE') + orderBy(postedAt)`처럼 등호 필터와 다른 필드의 정렬을 같이 쓰는 쿼리는 Firestore가 자동으로 색인을 만들어주지 않고 수동 복합 색인이 필요하다 — 배포 후 색인이 만들어지기까지 몇 분간 기능이 깨지는 위험이 있어 피했다. 대신 사업별 `entries`는 이미 D-65에서 자기 서비스 매출 열람을 위해 만든, 규모가 작고(그 사업 하나의 거래만) 단일 필드 정렬(`orderBy('postedAt')`)만 쓰는 조회를 그대로 재사용했다 — 학교 하나에 사업이 몇 개뿐인 규모에서는 이 방식이 색인 추가보다 안전하다.

**D-69. `ensureCommunityFund()`를 `businessRepository.ts`에도 그대로 복제했다 — `financeRepository.ts`의 것과 공유 모듈로 뽑지 않았다.**
소득세(D-59~62)와 사업 세금이 같은 `community-fund` 계좌를 쓰지만, 부트스트랩 함수 자체(3줄짜리 "없으면 만든다" 멱등 로직)를 공유 모듈로 분리하는 것은 지금 얻는 이득보다 새 파일/의존성을 만드는 비용이 크다고 판단했다(D-17의 "성급한 일반화 금지" 연장) — 두 스토어가 각자 독립적으로 같은 계좌를 준비하며, 먼저 실행되는 쪽이 실제로 만들고 나머지는 존재 확인 후 그냥 넘어간다.

## 과태료 1차 구현

**D-70. 신고(보고) 자체는 아무 금융 효과가 없다 — 학생이든 교사든 누구나 신고할 수 있지만, 교사의 결정(`decide`)만이 실제 `FINE` 저널을 만든다.**
원문 §24가 "학생이 임의로 과태료를 부과하지 못한다"고 명시한 대상은 **부과**(금융 실행)이지 **신고**(사실 보고)가 아니다. 그래서 `submitReport`는 활동 중인 멤버라면 누구나(학생 자신도, 교사도) 호출할 수 있게 열어 뒀다 — 신고 문서를 만드는 것만으로는 계좌·원장에 아무 영향이 없으므로 안전하다. 교사가 직접 목격한 위반을 처리하고 싶을 때도 "먼저 자기 자신에게 신고를 넣고 → 결정한다"는 같은 두 단계를 거치게 해, 별도의 "교사 직접 과태료" 경로를 새로 만들지 않았다(하나의 컬렉션·하나의 권한 모델로 두 경우를 모두 커버).

**D-71. 신고 원문(누가 신고했는지, 무슨 내용인지)은 신고자 본인과 교사만 볼 수 있다 — 신고당한 학생은 자기 계좌의 FINE 거래 내역으로 결과만 본다.**
또래 간 신고이므로, 신고 내용이 잘못됐거나 사춘기 갈등의 일부일 수 있다는 점을 고려해 "누가 신고했는지"와 "정확히 뭐라고 썼는지"는 대상 학생에게 노출하지 않기로 했다 — 이미 다른 모든 거래(월급·구매·세금)에서 학생이 "얼마가 왜 빠졌는지"만 보고 상대방의 내부 판단 과정은 보지 않는 것과 같은 개인정보 최소화 원칙(D-25 연장)이다. `violationReports`의 `get`/`list`는 `teacher(sid) || reporterUid==호출자`로 제한했고, 대상 학생은 이 컬렉션에 대해 아무 read 권한이 없다 — 대신 과태료가 실제 부과되면 자기 `accounts/{studentId}/entries`에 `label:'과태료'`로 정상적으로 나타난다(이건 이미 모든 학생이 읽을 수 있는 자기 거래 내역이므로 별도 규칙이 필요 없다).

**D-72. 신고 대상을 고르려면 학생도 반 전체 명단을 조회할 수 있어야 해서, `students`의 `list` 규칙을 교사 전용에서 "활동 중인 멤버 전체"로 넓혔다.**
1~2단계부터 `students.list`는 `teacher(sid)`만 허용했다 — 그때는 학생이 자기 반 전체 명단을 조회할 이유가 없었기 때문이다(자기 프로필은 `get`으로 충분). 과태료 신고는 처음으로 "다른 학생을 지목"해야 하는 학생 기능이라 이 가정이 깨졌다. 범위를 넓히면서 실제로 새로 노출되는 정보는 없다고 판단했다 — 학년 하나뿐인 작은 학급에서 이름·학년은 아이들이 이미 서로 아는 정보이고(사업 목록·구매 등 다른 화면에서도 이미 이름이 노출됨), `citizenCode` 같은 내부 식별자도 비밀번호가 아니다(로그인은 합성 이메일, D-44). 상한(`limit<=100`)은 그대로 유지해 대량 조회는 여전히 막는다. 클라이언트 쪽 `listActiveStudents()`는 `where('status','==','active')`로 서버 필터링하지 않고 전체를 받아 클라이언트에서 걸러낸다 — D-68과 같은 이유(등호 필터+다른 필드 정렬은 복합 색인 필요)로 새 색인을 만들지 않기 위해서다.

## 공동기금 지출, 그리고 Rules 복잡도가 실제 한계에 부딪힌 사건

**D-73. (긴급 구조 수정, 소득세·사업세·과태료 모두에 영향) `journals`의 `allow create`가 Firestore의 표현식 평가 한도(요청당 약 1000개)에 부딪혀, 조건이 참인데도 전체가 거부되는 사고가 실제로 발생했다 — `teacher(sid)`/`activeStudent(sid)`/`callerStudentId(sid)`를 매번 다시 계산하지 않고 `let`으로 한 번만 계산해 재사용하도록 고쳤다.**
공동기금 지출(`FUND_EXPENSE`)을 9번째 저널 타입으로 추가하자마자 — 새 분기 자체는 간단한데도 — 정상적인 지출 생성이 `PERMISSION_DENIED`로 거부됐다. 재현: 에뮬레이터에서 단계별로 분리해보니 저널 `create` 하나만 시도해도 실패했고, 새 분기를 최소화할수록(검증을 하나씩 빼볼수록) 성공 확률이 올라갔다 — 로직 버그가 아니라 **누적 비용** 문제라는 뜻이었다. 원인: `journals`의 `allow create`는 저널 타입마다 하나씩 OR로 묶인 거대한 조건식인데, 그중 7개 분기가 각자 `teacher(sid)`를(그때마다 `get(memberPath(sid))`를 새로 호출), 3개 분기가 각자 `activeStudent(sid)`+`callerStudentId(sid)`를(마찬가지로 각자 `get()`) 호출하고 있었다 — 저널 타입이 늘어날수록 이 중복 `get()` 호출도 선형으로 늘어나, 결국 한 요청이 평가해야 하는 총 표현식 수가 Firestore의 한도를 넘겼다.

고친 방법: `allow create: if journalCreateOk(journalId);`로 바꾸고, `journalCreateOk()` 함수 안에서 `let isTeacher = teacher(sid); let isActiveStudent = activeStudent(sid); let myStudentId = isActiveStudent ? callerStudentId(sid) : null;`를 딱 한 번만 계산해 모든 분기가 그 값을 재사용하게 했다. 각 분기가 실제로 검사하는 조건은 하나도 바꾸지 않았다(그저 반복 호출을 변수 참조로 바꿨을 뿐) — 그래서 기존 143개 테스트가 수정 없이 그대로 통과했다.

**재사용 가능한 교훈**: Firestore Rules에서 `assertSucceeds`가 실패하는데 조건식을 아무리 봐도 맞다면, 로직이 아니라 **평가 비용**을 의심한다 — 특히 하나의 `allow` 규칙이 여러 "종류"(저널 타입, 문서 상태 전이 등)를 OR로 묶어 처리하는 패턴에서, 같은 헬퍼 함수(그 안에 `get()`이 있는)를 분기마다 반복 호출하고 있지 않은지 확인한다. 최소 재현 스크립트로 조건을 하나씩 빼보면(이번처럼) "복잡도 문제"와 "로직 버그"를 빠르게 구분할 수 있다. 이 패턴은 `products`/`violationReports`/`accounts`의 `allow update`처럼 여러 분기를 가진 다른 규칙에도 잠재적으로 있을 수 있으나, 지금은 전부 테스트를 통과하고 있어 문제가 실제로 나타난 `journals`만 고쳤다 — 다음에 또 이런 실패가 나타나면 같은 `let` 메모이제이션 패턴을 그 규칙에도 적용한다.

## 경제 통계 1차 구현

**D-74. 경제 통계는 새 Rules나 색인 없이, 이미 있는 `accounts.list`(교사 전용, 상한 100)를 그대로 재사용해 클라이언트에서 집계한다.**
"유통 중인 마동"(§23의 경제 통계)은 학생·사업 계좌 잔액의 합으로 정의했다 — `system-issuer`/`community-fund`(`ownerType:'school'`)는 제도 그 자체(발행량·공동 재원)이지 시민 개인의 부가 아니므로 유통량 집계에서 제외한다. 서버 쪽 `where(ownerType==...)` 필터 없이 전체 계좌(최대 100개)를 받아 클라이언트에서 학생/사업으로 나누는 방식을 택했다 — D-68/D-72와 같은 이유로 새 복합 색인이 필요 없고, 이미 Rules가 허용하는 조회 그대로라 보안 규칙 변경도 전혀 없었다(이번 단계에서 유일하게 `firebase/firestore.rules`를 건드리지 않은 기능).

## 문서화 방식

**D-13. `docs/IMPLEMENTATION_PLAN.md`는 유지하고 새로 쓰지 않는다.**
해당 문서는 이미 원문 40개 항목을 구현 단위로 정밀하게 연결했고, Spark 무료 한도까지 실측 링크로 검증했다. 이번 작업에서는 화면 아키텍처 보정 사항만 짧게 append하고(§ "UI 아키텍처 보정 (신규)"), 나머지는 그대로 정본으로 유지한다. 이미 잘 작동하는 설계 문서를 이유 없이 다시 쓰지 않는다(원문 §77).
